# Distance-based camera history and transport repair

## 1. How to store the camera history

I agree that sampling every few seconds is wrong for this purpose. A stalled robot could spend several seconds looking at almost the same scene, replacing the earlier view that showed which port it approached. We should use **measured TCP travel along its path**: when the robot has traveled another threshold, save a synchronized frame from each of the three cameras. Keep the latest camera view live between milestones; a stall should not erase older route views. The distance is cumulative path length, so moving out and back still records the route. Reset the history at each episode reset. Save measured displacement and relative wrist orientation with each view so the model knows how the viewpoints relate. An in-place wrist turn or important contact could also trigger a view, because a distance-only rule misses those events; those triggers still need calibration.

I measured four thresholds on **ten saved, nonfinal SFP teacher routes** (581 sampled rows), rather than picking 40 mm by intuition:

| Travel between saved views | Median saved views per route | 90th-percentile projected target shift between views | Full routes fitting ten slots |
| --- | ---: | ---: | ---: |
| 20 mm | 13.5 | 83 image pixels | 0/10 |
| 30 mm | 10 | 111 pixels | 6/10 |
| 40 mm | 8.5 | 153 pixels | 10/10 |
| 50 mm | 7.5 | 164 pixels | 10/10 |

The image shift is computed *afterward* from simulator target geometry. It is a diagnostic, never an input to the deployed model, and does not prove the port was truly visible. At 40 mm, a normal large view change nearly spans the proposed 160-pixel crop. That is why I prefer **30 mm with up to 12 three-camera viewpoints** as an initial implementation. Twelve slots retain the whole teacher route in 9/10 recordings. We can cache each saved view's image features, so the image backbone need not rerun on all 36 historical frames at every control decision. This still needs a live latency check against the 300 ms limit. If twelve slots are too costly, ten slots at 30 mm with an explicitly protected early landmark are worth testing; simply changing to 40 mm risks missing the transition where the target enters or leaves a useful view.

For comparison, over a fixed 1.5-second gap, the measured travel ranged from **0.52 mm at p10 to 40.35 mm at p90**. In 230 of 571 consecutive roughly half-second intervals it was under 1 mm. Seconds are therefore a poor sampling clock for route memory. The ten recordings rarely show a projected target outside all camera bounds, so they **do not validate reidentification after it disappears**. Before using the distance rule for handoff, we need autonomous SFP and SC traces with actual visible/occluded target changes, target-identity labels, and full inference p50/p95/p99.

## 2. What to fix in transport later

**Known data gap.** The earlier 268 verified SFP episodes were highly skewed: 258 were card 0 / port 1. A later balanced set fixed that specific skew for a small supervised comparison: 50 successful, valid-command SFP teacher episodes across all ten requests, with ten separate development episodes. A separate set of 180 scored-successful replays covers targets but its recorded action arrays contain invalid zeros, so those are usable for scene/image analysis, not as direct BC action targets. The balanced actor still reached **0/3 safe buffered requested-port arrivals** in its frozen autonomous comparison. Thus balance alone did not solve closed-loop transport. We also have only limited useful examples of the actor's own early mistakes and teacher corrections; the ten corrective episodes added 2,302 teacher chunks but did not pass the autonomous gate. SC route coverage, alternate routes, starts, card arrangements, and recovery need their own episode-grouped audit before claiming they are sufficient.

**Known train/deployment mismatch.** The offline actor often sees the *teacher's* previous command as an input, whereas in deployment it sees its own previous command. An ablation in the prior SC/SFP audit showed large sensitivity to this field. If the actor deviates once, this input can reinforce the wrong route. A concrete repair is to train with the actually executed previous command from closed-loop traces, plus suitable corrupted/actor-generated prefixes, or ablate the previous-command input entirely and test the tradeoff. Keep the predicted output as a full TCP-body-frame target, not a residual correction or an absolute base-frame action.

**Known live error.** On the matched SFP development starts, the actor's measured route separated from the same-scene teacher by more than 10 mm around **3.85–3.95 seconds**. During the first 3–5 seconds its command sizes were typically smaller than the teacher's, with some direction disagreement. The precise cause is not proven, but it points to the *early route decision*, before precise pose estimation or insertion can help. The next targeted collection should begin at that divergence, not add routine full successful episodes. Compare the teacher's intended and robot's executed motion, the requested task code, the images, and the previous-action field on the same starts. Correct only the demonstrated early failure modes, then retest on complete new development episodes.

**Architecture hypothesis.** The present long-history transport actor uses frozen ImageNet ResNet-18 features from three cameras, measured state, task code, previous command and a small temporal transformer. Its history is selected by clock time, and its image features may discard detailed card/port layout. A separate route-stage probe could classify stage accurately but missed its **≤20 mm p95 next-waypoint** gate (48.2 mm p95), so simply adding a waypoint head is not yet a demonstrated fix. I would first replace time history with the distance memory above and test target-conditioned spatial camera features against the existing actor under the same data and budget. Auxiliary labels can teach route stage and next safe waypoint, while the one shared actor still predicts full TCP-body action chunks. If waypoint supervision remains inaccurate, do not feed it to the actor as though it were ground truth. A larger transformer or diffusion transformer by itself has no evidence of fixing the early route error; previous bounded comparisons did not establish a live gain.

**Proposed order and stopping rule.** (1) On frozen development traces, test whether 30 mm/12-view history improves correct-target crop availability and route-stage or next-waypoint prediction; compare with the old fixed-second history and profile full latency. (2) Do a matched actor-input ablation for previous commands and inspect the first four seconds of action direction, magnitude and measured movement. (3) If a specific early-route error is reproducible, collect a bounded set of teacher takeovers *from that error state*, train the same full-action actor, and compare against an equal-update control. (4) Promote only if new episode-grouped autonomous development starts improve safe requested-port arrival without extra harmful contact and full p95 inference remains below 300 ms. Then work on coarse handoff and near-port insertion. Final scenes remain sealed.

This is a design recommendation and offline audit; no new model was trained or deployed here.
