# Rootless Docker key quota: web research and options

## What matches this host

The current error is a known `runc` failure when container session keyrings hit the default **200 keys per non-root UID**. The same “disk quota exceeded” wording appears in [runc issue #726](https://github.com/opencontainers/runc/issues/726). The [Linux kernel key documentation](https://docs.kernel.org/security/keys/core.html) explains that `/proc/key-users` counts keys and keyrings separately from disk space and returns `EDQUOT` when a new one would exceed the account's quota. The [runc source](https://github.com/opencontainers/runc/blob/main/libcontainer/setns_init_linux.go) shows it joins a named session keyring when starting a container.

For UID 1008 here, `kernel.keys.maxkeys=200` and `/proc/key-users` currently shows **199/200** keys and **13,627/20,000** payload bytes. A five-second container probe changed usage from **199/200 → 200/200 while running → 199/200 after `--rm` exit**. While a separate probe container held the count at 200/200, `docker exec /bin/true` succeeded without increasing it; this matters because the Gazebo launcher uses exec inside its one container. Thus the one slot is reusable for sequential starts, but no second concurrent new container can rely on a free key. The 25 stopped AIC containers removed earlier did not change the baseline count. `keyctl list @u` found an empty user keyring; `keyctl reap` removed **zero** keys. The current session has no safe path to bulk-delete the old `_ses.<id>` keyrings. The active Isaac container remains running.

## Options, in order

1. **Ask the server administrator to raise the kernel quota.** This is the durable remedy for a shared rootless Docker host. A reasonable starting request is `kernel.keys.maxkeys=1024` and `kernel.keys.maxbytes=1048576`, with values chosen by the administrator for the whole server. The non-root sysctls are host-level administrator settings; they are not changed by `docker run --sysctl` inside a container. [Kernel documentation](https://docs.kernel.org/security/keys/core.html), [Docker's rootless configuration](https://docs.docker.com/engine/daemon).
2. **Use the current one-slot opening carefully.** Run one new rootless container at a time, keep the simulator process inside it while conducting a bounded sequence of non-final episodes, and cleanly stop it afterward. Check `/proc/key-users` before each launch. The five-second probe confirmed that the slot returns after clean exit, but a full Gazebo launch and repeated internal resets still need validation. This reduces keyring churn and avoids relying on multiple concurrent starts; it does not fix the underlying 199/200 state.
3. **After the active Isaac job is finished, plan a controlled rootless-Docker user-service restart or logout with a before/after key count.** An [open rootless BuildKit report](https://github.com/moby/buildkit/issues/6247) says restarting its container temporarily resolves the same error, which suggests this may release held references. That is only an analogy, not proof for this host. Do not restart the current rootless daemon while the Isaac job is active.
4. **Investigate which old session keyrings remain referenced.** The 195 visible `_ses.<id>` entries and their reference counts can be captured for an administrator. Deleting stopped Docker metadata did not free them. `keyctl reap` searches only accessible session-keyring trees for dead keys, so its zero result does not prove the old keys are in active use. [Keyctl manual](https://man7.org/linux/man-pages/man1/keyctl.1.html), [kernel garbage-collection notes](https://docs.kernel.org/security/keys/core.html).

## Options I do not recommend for the current active job

- **Revoking keyrings by guessed ID.** Old names do not establish that no process uses a keyring; revoking the wrong one could break a live process.
- **Changing Docker to use `runc --no-new-keyring` as a quick fix.** This option makes a new container inherit the caller's session keyring instead of getting a separate one. The separate keyring was added to prevent containers from affecting the daemon's keyring, so this weakens that isolation and would need careful runtime configuration. [runc option](https://github.com/opencontainers/runc/blob/main/man/runc-run.8.md), [original isolation rationale](https://github.com/opencontainers/runc/issues/453), [Docker alternative-runtime configuration](https://docs.docker.com/engine/daemon/alternative-runtimes/).
- **More `docker rm` or `docker system prune` just for this quota.** The 25-container cleanup already showed no measured key-count reduction. Further removal risks deleting useful layers without evidence it frees keys.

**Recommendation:** request the host-level quota increase now. Meanwhile, a sequential, bounded Gazebo test may be possible with the currently free slot; monitor the count, and stop new launches if it returns to 200/200. Keep the active Isaac container untouched.
