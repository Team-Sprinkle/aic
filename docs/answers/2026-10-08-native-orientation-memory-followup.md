# SC orientation-memory follow-up

I ran the bounded fixed-image check. The old SC audit retained JPEG camera frames, so I made one diagnostic repeat of the already used one-port Gazebo scene and saved the exact native RGB triplets losslessly, along with the measured TCP state and the earlier requested-port visual anchor. No model was trained, no insertion or RL was enabled, and no final scene was opened.

On the two fresh inspection frames, replaying **identical images and state** with memory off versus on gave the same result: the first inspection rejected a wrong tool posture, and the second accepted after posture correction. Both decisions used the current board reading. The absent-port request was rejected twice. The recapture did not naturally reproduce the earlier missing-board-lines failure, so this provides **no live evidence that memory improves handoff**. Posthoc Gazebo geometry at acceptance showed **0.130 mm** opening-position error and **2.11°** true tool-posture error, within the configured 3° check.

I then forced just the board-line detector to report no lines on those same saved images. This **synthetic code-path test** made the no-memory checker reject both frames. Memory rejected the wrong posture, accepted the corrected posture, and still rejected the absent port. It confirms that the fallback logic is wired correctly; it does not show how often the natural failure occurs or whether a live rollout improves.

The orientation-memory option stays **off by default**. I stopped further routine repeats of this scene. The next useful work is the separate SFP transport-arrival gate: only one of six saved autonomous routes entered the stop corridor, so improving the visual stop alone cannot produce reliable handoff. Any new transport fit should have a concrete route-label hypothesis and a grouped development gate before more Gazebo rollouts.
