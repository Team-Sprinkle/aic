# Is one sequential container enough?

**Correction after a full Gazebo run:** The minimal probe below was insufficient. One complete Gazebo teacher rollout finished successfully but left UID 1008 at **200/200** keys after its container exited. The subsequent separate extraction container failed at startup. Host MCAP extraction now works, but another Gazebo launch remains blocked until the key count falls or an administrator raises the quota. See [fresh shadow check](../experiments/2026-10-04-sfp-fresh-anchor-shadow.md). The text below describes the earlier probe, not a currently working ten-rollout schedule.

**Yes for the next bounded SFP development check.** The account currently has 199/200 kernel keys. A new container occupies the last slot while it runs and cleanly returns the count to 199/200 when it exits. I tested the important extra step used by our launcher: while a probe container held the quota at **200/200**, `docker exec ... /bin/true` succeeded and the count stayed 200/200. Thus the current launcher can start **one** fresh Gazebo container, use `docker exec` inside it, stop/remove it, and then launch the next episode. The full Gazebo workflow still needs a real smoke test; the keyring part of that workflow passed.

The recent SFP feasibility and balanced-teacher scripts already use a sequential `for` loop with blocking `subprocess.run` for each episode. The rollout shell creates one Gazebo container, uses several `docker exec` calls inside it, and stops/removes that container on exit. During those runs, the old Isaac container could remain active, so the likely total is **two simultaneous containers: one Isaac plus one Gazebo**. More GPU processes may run on the host without being additional Docker containers. [Pilot script](../../scripts/run_sfp_cheatcode_target_pilot.py), [balanced collector](../../scripts/collect_sfp_balanced_teacher_bags.py), [Gazebo launcher](../../scripts/run_clean_transport_eval.sh).

We have sometimes used more. The September ACT comparison explicitly records **three isolated rootless simulator containers** active in that older setup, using physical GPUs 0–3. That is a historical example, not the normal requirement for the current ten-scene SFP check. [Older ACT record](../experiments/2026-09-17-act-verified-8h.md).

For the next **ten fresh, non-final SFP resets**, sequential execution is enough for correctness and should be practical, although it takes longer than parallel evaluation. No additional Docker container is needed to run the frozen offline perception analysis on the host. Keep the one-Gazebo launch order explicit and check `/proc/key-users` before each start. This single-slot arrangement is **not enough for two new simulator containers at the same time**, and it is fragile if another process under UID 1008 creates a key. Larger parallel collection or RL will benefit from the administrator's quota increase. The number of GPUs and the number of containers are separate limits; one container can be given more than one GPU.
