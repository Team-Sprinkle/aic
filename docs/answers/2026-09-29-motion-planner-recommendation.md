# Motion planner recommendation

**Use MoveIt 2 with OMPL's RRTConnect for the next Gazebo teacher-route experiment.** It fits this repository: the evaluation stack uses ROS 2 Kilted, and we already have a [MoveIt configuration](/data1/chmin/yj/ws_aic/src/aic/aic_moveit_config/config/ompl_planning.yaml) and a [MoveItPy backend](/data1/chmin/yj/ws_aic/src/aic/aic_teacher_official/aic_teacher_official/expert_generator/moveit_py_backend.py). MoveIt can plan collision-checked robot joint paths around objects in its planning scene; the official [MoveIt planning documentation](https://moveit.picknik.ai/main/doc/concepts/motion_planning.html) describes this use, and its [Python API](https://moveit.picknik.ai/main/doc/examples/motion_planning_python_api/motion_planning_python_api_tutorial.html) supports scene objects and pose goals. For offline expert collection, a planning call lasting seconds is acceptable; the 300 ms limit still applies to the autonomous policy at inference time.

There is an important limit: **MoveIt plans the arm, not the deforming cable.** A path can clear every robot/card collision check while dragging the cable over a card. cuRobo has the same fundamental limitation for this task: its documented collision model checks robot geometry against cuboids, meshes, or depth-based maps; it does not supply our cable dynamics automatically. cuRobo is attractive when we need fast GPU planning, but its [robot/world setup](https://curobo.org/get_started/2c_world_collision.html) would add integration work without solving cable routing by itself. I would keep it as a second candidate if MoveIt planning speed or success becomes the measured bottleneck.

I would use MoveIt for the *shape of the robot motion*, with only a small amount of task-level guidance: choose an outside-left or outside-right corridor around the five cards, forbid crossing over the card row, and ask MoveIt to connect the start, corridor, and pre-insertion region. This lets the planner choose joint configurations and collision-free paths rather than interpolating our hand-written TCP waypoints. Gazebo should then execute and score each plan, including the actual cable path, force, insertion depth, and video. The final short insertion remains a separate contact-control step.

**First repair the existing integration.** The current [backend](/data1/chmin/yj/ws_aic/src/aic/aic_teacher_official/aic_teacher_official/expert_generator/moveit_py_backend.py) calls `plan()` but does not put `scene_snapshot.collision_objects` into MoveIt's planning scene; it even returns an empty `planning_scene_objects` list. The [scene extractor](/data1/chmin/yj/ws_aic/src/aic/aic_teacher_official/aic_teacher_official/expert_generator/collision_scene.py) also makes coarse boxes from config values, so card positions, yaw, gripper/plug geometry, and collision margins need checking against the actual Gazebo scene. Otherwise, a successful MoveIt plan would not prove it avoided the cards.

**Bounded pilot:** On the existing five-card hard scene, try both SC target ports and several reset starts. Compare the repaired MoveIt route with the scripted route using full-insertion rate, cable/card clearance and visible draping, peak force, plan failures, and planning time. Require the cable to stay beside the row in the recordings. If MoveIt improves those outcomes, extend to other card counts and positions; if it only improves rigid-arm clearance, revise the corridor or cable-risk model before collecting more teacher data. Keep simulator geometry confined to teacher generation and diagnostics; the deployed visual policy still cannot use privileged poses.
