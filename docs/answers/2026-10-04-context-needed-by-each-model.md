# What context does each model need?

Yes. A close-up can show a socket clearly while hiding **which card and which of its two ports** it belongs to. The task code says “card 2, port 0,” but it does not tell the camera where card 2 is. To make a safe handoff, the system needs either enough of the whole card row in the current views or a trustworthy earlier view that established the identity, carried forward using measured robot motion. If neither exists, it should say **unknown** and seek a better view. A longer history cannot recover information that was never observed.

An example: the wrist camera sees two similar openings after approaching a five-card rack. An original-resolution crop may locate an opening very precisely, yet still select the wrong card. Earlier wide views could establish the order of the cards. The robot would then track the requested card through its measured motion and confirm the close-up against that track. **Simply requiring several consecutive predictions to agree is insufficient:** our SFP tests produced stable, coherent wrong-port predictions.

| Function | Context supplied now | Context that is missing or not yet reliable |
| --- | --- | --- |
| **Transport** | Three camera views, public task code, measured robot state, previous proposed action chunk, measured TCP motion and timing; the temporal actor can use 17 sampled observations across about 60 seconds. | A reliably grounded route stage or safe next subgoal, and enough feedback from its *own* off-route attempts. Offline histories contain teacher commands whereas live histories contain the actor's commands. The transport actor has history already, so adding more frames alone is unlikely to solve its closed-loop drift. |
| **Requested-port camera check** | Current RGB from three calibrated cameras, task code, measured TCP, a coarse candidate and an original-image crop, plus geometric and force checks. An SC approach-history anchor has been tested only in a shadow diagnostic. | A reliable wide-view identification of the requested card/port, request-specific tracking to the close-up, true per-camera identifiability rather than mere image projection, and a rule to abstain when views disagree. Current SFP heads can confidently choose a neighbor; the SC history idea is not a promoted handoff. |
| **Insertion** | Current RGB, measured state, task code, and estimated TCP pose relative to the estimated port; its actor predicts complete port-frame tool targets. | Validity and uncertainty of that estimated pose, recent measured insertion progress versus commanded movement, force/contact trends, and explicit phase information for approach, seating and blockage. Training also needs handoff states produced by the transport actor, not only clean teacher starts. Whether each added input improves insertion must be tested. |
| **Recovery** | Force and robot motion can be observed, and backtracking logic has been explored. | Memory of where it has already backed off and which lateral routes failed; recent force, motion and contact trends; and evidence of cable tension or snag when visible. A single current image or force sample cannot reliably distinguish a port lip from a snag elsewhere. Some cable state may remain unobservable from the permitted cameras. |

The most consequential gap today is **identity memory at the transport-to-insertion handoff**, alongside transport's own route reliability. I would represent that memory as a small, task-specific hypothesis: “this observed card is the requested card; this is its requested port; these images established it; this is how far the robot has moved since; and this is whether fresh images still support it.” Reset it on every episode or task change. Keep both a wide image for card order and an original-resolution crop for precise geometry. Use camera timestamps and per-camera calibration when associating the three views. A history entry must have an independently credible identity; otherwise carrying it forward preserves a mistake.

I would test this as an **information sufficiency audit before training another model**. On existing, complete development episodes, review where the requested port is actually identifiable in each camera and whether an earlier wide view resolves card order. Compare a current-frame check with an observation-only history tracker, including known wrong-card, wrong-port and occluded cases. Measure wrong accepted handoffs, correct coverage, errors after the robot moves, and complete inference latency. Keep the reserved final scenes sealed. If even the earlier images do not establish identity, the next change should be a better viewpoint or observation strategy. If they do, build and validate the tracker. Either way, the model should be allowed to return **unknown** rather than inventing a pose.
