# Transport route-restore check: result

I continued with the bounded restore check. Gazebo can save and set its entity-component state, but that is not the complete state of this running robot task. The AIC controller also holds its current target and interpolation progress in a separate process; the cable plugin holds its attachment state internally. The existing joint-reset service resets selected joints to an initial pose instead of restoring the saved robot and cable.

This failed the predeclared prerequisite for fair same-state route comparison. I therefore did **not** run two purported AIC “restores” or claim a TCP/cable/force fidelity score: such runs would start with uncontrolled differences. I ran only a disposable rootless Gazebo service probe, with **no GPU and no model training**. The full [experiment record](../experiments/2026-10-10-sfp-state-restore-feasibility.md), [machine decision](../../outputs/experiments/2026-10-10_sfp_state_restore_feasibility_v1/decision.json), and [service output](../../outputs/experiments/2026-10-10_sfp_state_restore_feasibility_v1/service_probe.txt) preserve the evidence. The probe container was removed, and the unrelated existing Isaac job was untouched.

**Next direction:** close exact-state route ranking for now. The proposed next test first counts existing contact-labeled actor resets. If those are too sparse, a targeted diagnostic would use at most 30 training and ten new development resets, one GPU and four hours of Gazebo time. It would ask whether camera history adds useful warning of cable contact within one second over robot state, route and force alone. The proposed gate is ≥90% held-out contact recall with ≤20% false alarms and a material improvement over the simpler baseline; only then would we try at most three autonomous feedback starts and require ≥2/3 safe buffered arrivals. These are proposed stopping rules, not measured results. Existing stage-label and cable-safety gates remain open; handoff, insertion, RL and final scenes remain sealed.
