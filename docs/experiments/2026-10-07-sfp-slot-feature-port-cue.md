# SFP slot-feature port cue: bounded diagnostic

The proposed shared board map must generate a requested-port cue *before* a fine crop or actor handoff. A frozen all-port RGB detector's ten three-view candidate points contained the actual requested opening within 20 mm early in only **4/10** saved grouped development scenes, even when candidate card labels were ignored. It named the requested channel correctly in 3/10. Thus candidate renaming alone has a 4/10 upper bound on this replay. The new test trains a port cue from local features at the board model's **predicted** slots, retaining the full three-camera images and public measured TCP. Projected port points are supervised labels only. [Frozen candidate-set audit](../../outputs/experiments/2026-10-07_sfp_candidate_set_ceiling_v1/summary.json).

## Frozen protocol before fitting

- Initialize and freeze the existing slot-local board model, which previously reached 10/10 occupancy maps on grouped development and another ten scenes. Its predicted two rail endpoints and local features around the five interpolated slots are observation-derived. A small shared head reads those features, global image context, measured TCP, camera/slot/port codes, and the predicted slot pixel to output all ten port pixel locations plus in-frame probabilities. At runtime the public request selects one output. Never use a projected true port, per-scene board pose, or simulator geometry to select a slot/crop.
- Train on the existing 70 complete-reset SFP training groups, all present ports per frame; select checkpoints only on the ten existing grouped development scenes. Budget: one GPU, at most 2,000 head updates and 30 minutes. Keep the board backbone frozen. Preserve every checkpoint score.
- Offline gate: **zero accepted wrong-port points**, requested opening acquired in the first three saved seconds in **at least 9/10** development groups, accepted 3D p95 **≤20 mm**. Acceptance uses all three predicted in-frame flags ≥0.5 and reprojection ≤5 px. If the gate fails, stop before any new-scene or actor test. If it passes, freeze and test once on untouched nonfinal groups, then measure complete live p95 against 300 ms before an actor comparison. Final scenes stay sealed.

This diagnostic is distinct from the failed pooled all-port heatmaps and the failed fixed rail/TCP coordinate prior: it conditions on local original-image slot features at the requested structural position. It is still vulnerable if the predicted board origin is wrong or no visual evidence of a slot exists; those failures must be reported, not threshold-tuned away.

## First fit result and one targeted architecture repair

The first fit's two startup attempts stopped before a model update because forked data workers stalled after CUDA initialization, then spawned workers oversubscribed CPU via OpenCV. Their reasons are preserved in `outputs/experiments/2026-10-07_sfp_slot_feature_port_cue_v{1,2}/failed_startup.json`. Version 3 used spawned workers with one OpenCV/Torch thread each and completed all **2,000** updates. Its best development checkpoint was step 1,500: **one accepted row, zero wrong, early correct in 1/10 groups, 11.93 mm accepted p95**. Step 2,000 had three accepted rows but still only 1/10 early groups. In the step-1,000 predictions, all 119 rows passed the predicted occupancy and in-frame flags but failed the **5 px three-camera reprojection gate**; residual median was about **42.8 px**. This is a cross-camera 3D-consistency failure, not a low occupancy score. No new-scene or actor test follows from this checkpoint. [Checkpoint, all eight development evaluations and predictions](../../outputs/experiments/2026-10-07_sfp_slot_feature_port_cue_v3/summary.json).

One bounded repair follows this specific failure: predict **one shared 3D port point in the base frame** from the same frozen three-camera slot features, measured TCP and slot/port code. The head parameterizes it as a base-frame displacement from measured TCP position. Projecting that single point into each camera makes its views geometrically consistent by construction. Train a small head on the same 70/10 complete-reset split, at most 2,000 updates/30 minutes on one GPU. Add one predicted uncertainty scale so the model may abstain. Freeze an acceptance rule **before training**: requested slot occupied, predicted uncertainty ≤20 mm, and predicted port projects into all three cameras. Require zero accepted wrong-port points, at least 9/10 early correct groups, accepted 3D p95 ≤20 mm and report unconditional 3D error and uncertainty calibration. If it fails, stop this representation branch; do not merely relax the uncertainty threshold or train the actor.

**3D repair result:** All 2,000 updates completed. The predeclared selected step 1,250 accepted 119/119 development rows, including **five wrong neighboring ports**; accepted 3D p95 was **39.75 mm** and only **48.7%** of accepts were actually within 20 mm despite predicted uncertainty ≤20 mm. The median predicted uncertainty was about 7–9 mm by request while median actual errors often exceeded 20 mm. At update 2,000 unconditional p95 improved to 33.17 mm but wrong accepts rose to 13; choosing that checkpoint would not pass either. The shared 3D representation removes reprojection disagreement but does **not** establish correct target identity or calibrated abstention. Stop this representation branch. No new-scene test, actor training, handoff or RL follows from it. [Full history and per-row results](../../outputs/experiments/2026-10-07_sfp_slot_feature_port_3d_v1/summary.json).

## Separate privileged-cue upper bound on transport, not a deployable actor

The 3D cue failure leaves one causal question: if a transport head were handed the **true requested port relative to measured TCP** as a *diagnostic oracle*, could the existing frozen temporal representation learn better first actions? This uses ground truth during both train and evaluation and can never be promoted. The existing 50 balanced SFP train reset groups and ten disjoint grouped development resets join exactly by scene hash/request to the geometry label manifest; unmatched rows are excluded. Precompute the frozen actor's temporal 256D hidden vector once and train two identical small full-action heads for at most 1,000 updates: one receives zeros, the other receives true TCP-relative 3D port translation. Same rows, sampler, seed, update budget and loss. Compare held-out first-action p95 overall and at 0.3–1.2 s. Require ≥20% improvement in early p95 without worsening overall p95 to justify a later *predicted-cue* transport design. If oracle does not help, investigate route/action supervision or frozen representation. No live run, final-scene access or actor promotion from this diagnostic.

The first matched fit (`sfp_oracle_transport_cue_v1`) used unscaled metre coordinates. Zero-cue and oracle early p95 were 1.90521 and 1.90563 mm, and the learned cue columns of the first linear layer had norm 0.0398 versus 9.415 for hidden-feature columns. The raw cue components are generally 0.01–0.2, so this run did not give the oracle input a fair numerical scale. Preserve it as a failed implementation diagnostic. One fixed repair divides both train and held-out oracle cues by **0.1 m**, with the same architecture, rows, updates, seeds and zero-cue control; stop after that matched rerun.

**Normalized oracle result:** Both heads completed 1,000 matched updates. On the 651 held-out teacher rows from ten complete development resets (40 early rows), the zero-cue head reached **1.905 mm** early first-action p95 and **2.019 mm** overall p95. The privileged true-cue head reached **1.850 mm** early p95 (**2.89%** improvement) and **2.029 mm** overall p95 (slightly worse). This misses the declared 20%/no-overall-regression gate. The ten per-request p95 values and all five checkpoint scores are preserved in `outputs/experiments/2026-10-07_sfp_oracle_transport_cue_v2/`. This comparison concerns *teacher-observation one-step action imitation* with teacher-command history and a frozen temporal representation. Its already-low ≈2 mm errors leave little room to improve, and they do not predict autonomous route stability. Therefore it neither validates nor disproves a target-aware transport actor in off-route states. It does rule out this cheap frozen-head cue attachment as the next transport repair. No oracle model was run live or designated deployable.

## Stop decision and next experiment

All predeclared gates in this branch failed. The candidate-set diagnostic found a missing correct physical point in six of ten early groups; the local 2D head produced cross-camera disagreement; the single-3D head produced wrong-card and overconfident errors; the cheap oracle transport head did not yield a meaningful teacher-action gain. Do not continue crop-width, confidence-threshold or frozen-head sweeps on these same development scenes. The current selected-port handoff and insertion switch remain disabled. No new Gazebo collection, actor/RL run, or final-scene access occurred here.

The next genuinely distinct **perception** hypothesis is a temporally maintained board-coordinate map with an observable slot-zero reference, trained on original RGB and measured TCP travel and able to abstain when the reference is absent. First obtain an independent review of the frozen observation-complete 30-panel packet at `/home/nas/chmin/aic_archives/2026-10-07_sfp_blind_review_followup_v1/`; the first RGB-only review omitted public TCP state. If the complete observation cannot establish slot order in early views, test one safe *earlier* inspection posture that reveals the board origin, before fitting another model. This is a plan revision, not a passed gate. For transport, the next comparison must include autonomous off-route states and explicit target-dependent route supervision, not only matched teacher-action p95. A deployment actor may consume **predicted** target cues only after the independent identity gate passes. Keep ≤4 GPUs, rootless runtime, 300 ms complete inference and sealed final starts.
