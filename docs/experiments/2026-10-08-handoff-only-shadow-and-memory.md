# Frozen handoff-only diagnosis on autonomous routes

Date: 2026-10-08. The question is whether autonomous transport can hand over the *requested* port safely, separately from insertion and cable/contact recovery. Models and scene choices were frozen before the new SC runs. No insertion actor, RL, privileged policy input, or final-scene evaluation is enabled.

[Machine decision](2026-10-08-handoff-only-shadow-and-memory.decision.json) records the accepted counts, artifacts and promotion gate.

## Evidence and experiment design

The preceding plain SC BC comparison made 0/16 stable 10 mm arrivals, whereas a different SC visual-standoff controller accepted 4/4 two-port shadow handoffs but subsequently missed a valid one-port arrival. The recent corrected SFP actor reached only 1/3 safe buffered arrivals and once branched toward the wrong card without contact. These observations call for family-specific shadow tests, not pooling the two SC controllers.

For SC, `scripts/prepare_sc_llb_collection.py` created ten random legal nonfinal resets with seed `20261008` and indexes 900–909. Before running, `frozen_selection.json` fixed four: 900 (one card, port 0), 903 (four, port 1), 904 (five, port 0), and 909 (five, port 1). The full reset hashes are in the [frozen manifest](/home/nas/chmin/aic_archives/2026-10-08_handoff_only_new_sc_v1/frozen_selection.json). The existing SC temporal actor, visual standoff controller, original-RGB locator, identity head, refiner and board orientation estimator were frozen. A rejected posture check can correct orientation while holding the measured TCP and requires another fresh-image inspection. A counterfactual request for the other port is logged but never affects action. Causal history is diagnostic only. `scripts/run_sc_shadow_handoff_pilot.sh` runs the rootless, transport-only Gazebo scene; only selected-port observation, public task code and measured robot state affect control. Gazebo TF is read afterward for scores.

The first launch for 900 was invalid: the launcher did not supply the TCP-base handoff-region veto now required by `RunTemporalTransport`. Policy instantiation failed; this run is excluded from the denominator. Its raw logs remain under `rollout_llb_0900/`. The exact train-fitted broad veto has been copied to `configs/hierarchical_recovery/train_handoff_tcp_regions_20261005.json`, and the SC pilot launcher now provides it by default. The valid 900 run used the same prior through an explicit environment variable; the evaluator completed. A fourth-start launch also failed before creating an audit because the shell read its launcher while that file was being patched; it was restarted separately with the frozen models and scene. Neither invalid launch is a model result.

Two additional nonfinal one-port variants were frozen before stress evaluation: copies of random resets 900 and 909 with the *other* SC port physically absent. The selected port and randomized robot/board/cards remain the same. They are at [one-port manifest](/home/nas/chmin/aic_archives/2026-10-08_handoff_only_new_sc_v1/oneport_stress/manifest.json). This probes the known valid-arrival identity miss and absent-port false accepts.

For SFP, the latest selected-port original-RGB board-and-crop checkpoint was replayed on the three already scored autonomous corrected-actor routes (2, 3 and 5 cards). `scripts/replay_sfp_selected_port_handoff_shadow.py` selects a causal camera frame from each proposal's recorded image timestamp, runs the frozen requested-port model every 0.5 s, then opens Gazebo geometry **only to score** the frozen predictions. The first replay used nearest frames and could select a later frame; it is superseded by the causal-frame `..._causal_v2.json` result. `scripts/analyze_sfp_causal_port_anchor.py` tests a request-bound two-agreeing-view memory with a 5 mm agreement and 150 mm measured-travel expiry. This is an offline shadow diagnostic, not a deployed stop. The [causal SFP predictions](/home/nas/chmin/aic_archives/2026-10-08_handoff_only_sfp_shadow_causal_v2.json) and [anchor analysis](/home/nas/chmin/aic_archives/2026-10-08_handoff_only_sfp_anchor_causal_v3.json) contain every sampled prediction, source frame, model hash, scoring label, and decision.

No current image was accepted at either true-buffer sample in the three-card route. The causal selected-port anchor was still available at both, with **1.37 mm** posthoc 3D error and correct requested-port identity. This supports memory for *retaining* an earlier visual estimate on that route, but the other two actors did not arrive. It does not prove insertion-grade pose, orientation, true visibility, or a safe switch. Naively stopping when TCP is 70–100 mm from the anchored 3D point would make **three false candidate stops** on the two-card wrong-lateral route (actual lateral 36–39 mm). Thus position distance alone is explicitly rejected; a port-frame axial/lateral and orientation check or independently validated visual docking state is necessary. The saved `inference_ms` times cover the warmed model forward pass, not image capture, ROS, or insertion actor.

A second read-only ablation fused a frozen full-port-pose cascade with the accepted requested-port *position* anchor. It admitted a full pose only when its position agreed with the selected-port model within 5 mm, then required two pose observations within 2 s and 5 mm with at most 3° mutual orientation difference. It computed the stop corridor from the **predicted** port frame: axial distance 70–100 mm on the approach side and lateral distance ≤10 mm. True Gazebo port geometry entered only the later scoring pass. On the three corrected-actor routes, the one three-card route that actually visited the corridor had **2/2** matched stop candidates and **0** false candidates; the other two routes had no corridor visit and correctly abstained. On the three matched baseline-actor routes there were no corridor visits and no stop candidates. These are **one arriving route among six**, so the result supports the orientation-aware check as a possible shadow gate, not a reliable autonomous stop. The frozen model forward path measured about 17–18 ms p95 in replay, excluding image decode, ROS, transport actor and insertion actor. See [corrected-actor pose fusion](/home/nas/chmin/aic_archives/2026-10-08_handoff_only_sfp_anchor_orientation_v1.json) and [baseline-actor pose fusion](/home/nas/chmin/aic_archives/2026-10-08_handoff_only_sfp_anchor_orientation_baseline_v1.json); both include every candidate and true-buffer label. ### One-port stress and bounded orientation-memory repair

The frozen one-port baseline gave a useful controlled contrast. On the new one-card **port-0** scene 900, transport came within **0.931 mm** of the true standoff, but all three fresh inspections rejected with `insufficient_board_rails`. Their requested-port identity scores were roughly 0.98–0.99 in every camera and the three-view refined opening reprojection was 0.30–0.48 px. The opening and requested identity were available; the close-view board-line yaw estimator was not. Earlier causal history samples on the *same rollout* did have two-view-consistent board yaw and a requested-port opening anchor. I viewed the center, left and right saved images at 48.8 s; the blue target is visible and the board grooves remain visible in the images, but the fixed line filter does not retain enough qualifying rails. Posthoc scored TCP posture remained about **5.7°** wrong at all three holds, so simply accepting the port position would be unsafe. The baseline held, failed and timed out with no insertion. On the new five-card **port-1** one-port scene 909, the unchanged stack accepted at its first fresh inspection: opening error **0.195 mm**, true TCP posture error **0.170°**, and the physically absent other-port counterfactual was rejected. These are two development stress scenes, not a reliability estimate.

The targeted opt-in repair stores a request-bound port orientation **only when** an earlier original-RGB inspection has accepted selected-port identity in all cameras, ≤2 px opening reprojection, at least two consistent board views within 1°, and acceptable measured force. Later, if fresh board lines are insufficient, the verifier may use that saved orientation only if the arm traveled ≤150 mm since its last qualified refresh, the **fresh** refined opening agrees with the saved opening within 5 mm, any single currently valid board view agrees within 2°, and the fresh identity, posture, standoff and force checks still pass. Conflicting current board views are never overridden. The flag is `AIC_SC_SHADOW_USE_HISTORY_ORIENTATION=1` and is off by default. `SCShadowHandoffVerifier.inspect` exposes `orientation_source` in its report. A saved-JPEG replay at 48.8 s exercised the fallback and correctly returned `wrong_tcp_posture` at ~4.9°, instead of incorrectly accepting. The original live native RGB failed rail detection at that point; the JPEG replay is a code-path check, **not** a live result.

Two further nonfinal one-port resets, 910 (port 0, one card) and 919 (port 1, five cards), were frozen **before** running the repaired verifier. Their [independent manifest](/home/nas/chmin/aic_archives/2026-10-08_handoff_only_new_sc_v1/independent_oneport/manifest.json) is separate from the scene-900 development repair. The candidate must first repair the scene-900 valid-arrival miss without accepting a wrong/absent target; then the independent pair checks transfer and regression. The actor, scenes, stop thresholds and insertion-disabled mode are otherwise unchanged. A fresh model or policy fit is not justified by this small visual-yaw failure.

### Matched one-port result and decision

The candidate run on the already diagnosed scene 900 accepted the correct port at its second inspection (posthoc opening error **0.162 mm**, true TCP posture error **0.555°**), but its `orientation_source` was `current_board`. Its first inspection rejected a real **5.26°** posture error. Thus this same-scene pass cannot be attributed to the new memory path; the earlier baseline's rail failure and this candidate's fresh rail success differ between Gazebo repeats.

The independent comparison used the exact same frozen 910 and 919 reset configurations, actor and models in both arms. Only `AIC_SC_SHADOW_USE_HISTORY_ORIENTATION` differed. Gazebo trajectories differed slightly between repeats, so this is a matched-scene, **not bitwise paired-trajectory**, test. [Four-run machine summary](/home/nas/chmin/aic_archives/2026-10-08_handoff_only_new_sc_v1/independent_four_summary.json) and each run's scored stream, posthoc geometry and recall are in the archive.

| Independent one-port scene | Flag off | Flag on | What changed |
| --- | --- | --- | --- |
| 910, one card, port 0 | Accepted after rejecting a 4.19° true posture error; opening 0.188 mm; closest standoff 0.532 mm | Accepted after rejecting a 4.55° true posture error; opening 0.145 mm; closest 0.819 mm | Both acceptances used `current_board`; no memory fallback was needed. Both had no scored contact. |
| 919, five cards, port 1 | No inspection; closest true standoff **281 mm**; card/gripper contact scored | No inspection; closest **187 mm**; no scored contact | Both stopped at bounded runtime, far from the requested port. The visual verifier and memory path were never tested there. |

The independent 910 proposal inference p95 was **200 ms off / 193 ms on**, and verifier p95 was **88 ms off / 100 ms on**; 919 proposal p95 was **200/190 ms** with no verifier call. These are live per-decision measurements, not a complete connected handoff-to-insertion latency. No run accepted an absent sibling port; in the accepted scene, the counterfactual absent-port request was rejected. No run inserted because the experiment is shadow handoff only.

**Decision:** keep orientation memory opt-in and **off by default**. It made no causal accepted decision in the live comparisons. The scene-900 failure mechanism is real and its saved-JPEG replay exercised the fallback safely, but the proposed repair has no independent live benefit yet. Further routine data collection or retraining under this hypothesis stops. The remaining independent 919 failure is upstream transport reachability, not a visual rejection. A future bounded repair should replay a fixed native-RGB sequence that contains a qualified earlier board observation and a later rail failure while the measured posture is corrected, then run a small set of genuinely new one-port arrivals only if that deterministic handoff logic changes the decision without an absent-port accept. Keep final scenes sealed. For SFP, improve autonomous requested-port transport before judging stop recall: only one of six archived routes entered the corridor, even though the visual fusion recognized its two sampled visits. This is why neither automatic insertion switch nor RL is enabled by these results.

### Follow-up: fixed lossless native-image replay

The old scored bag contains controller, wrench, joints and TF, **not camera-image topics**. Its separate `frame_manifest.csv` points to JPEGs. A native-image replay from that recording was therefore impossible. I added an opt-in diagnostic snapshot path (`AIC_SC_SHADOW_NATIVE_SNAPSHOT_DIR`) to `RunTemporalTransport`: it saves the exact original 1024×1152 RGB triplets losslessly as PNG, the measured 32D state, request, and previously qualified observation-only anchor. It has a capture cap and is not read by the policy. A single controlled repeat of the already used nonfinal one-port scene 900, with memory off, saved seven qualified earlier triplets and two fresh inspection triplets in [the lossless snapshot folder](/home/nas/chmin/aic_archives/2026-10-08_handoff_only_new_sc_v1/native_replay_capture_llb0900/native_shadow_frames/). This was a diagnostic recapture to fill the missing input artifact, not a new held-out result.

`scripts/replay_sc_native_orientation_memory.py` then made three decisions on each **identical** saved native triplet and measured state: baseline without anchor, candidate with its causally prior request-bound anchor, and an adversarial physically absent sibling-port request given that same anchor. The [fixed native replay JSON](/home/nas/chmin/aic_archives/2026-10-08_handoff_only_new_sc_v1/native_replay_capture_llb0900/native_memory_replay.json) includes model and PNG hashes. At 45.85 s both baseline and candidate rejected `wrong_tcp_posture` (3.62° predicted error). At 48.20 s both accepted the requested port after posture correction (0.58° predicted error). Both decisions used `current_board`; the absent-port request was rejected at both times. Counts: baseline accepts **1/2**, memory accepts **1/2**, memory-only accepts **0/2**, absent-port accepts **0/2**. All eight approach-history checks in this repeat had usable board orientation or a separate opening-view disagreement; none reproduced `insufficient_board_rails`. The captured center view visibly shows the blue target and board rails. This exact native replay demonstrates no regression on those frames and **does not validate the memory repair**. The one-port memory branch remains off, and another routine same-scene rerun is not justified.

The [posthoc Gazebo geometry score](/home/nas/chmin/aic_archives/2026-10-08_handoff_only_new_sc_v1/native_replay_capture_llb0900/posthoc_geometry.json) gives **0.130 mm** selected-opening position error and **2.11° true TCP posture error** at the accepted inspection, below the current 3° posture gate but larger than the verifier's predicted 0.58°. Closest true transport standoff was **0.916 mm**; the official score remained zero because insertion was disabled. This is further reason to retain the strict posture check rather than relax it to recover one missed handoff.

A separate **synthetic detector-failure check** kept those same native RGB pixels, selected-port model, measured states and anchor, but forced the board-line detector to return no lines. This is an isolated code-path test, **not a naturally occurring Gazebo failure**. Without memory, both inspections rejected `insufficient_board_rails`. With memory, the first still rejected wrong TCP posture and the second became a memory-only accept; both absent-port requests still rejected. The earlier/fresh opening anchor agreed within **0.124/0.082 mm**. [Synthetic-dropout replay](/home/nas/chmin/aic_archives/2026-10-08_handoff_only_new_sc_v1/native_replay_capture_llb0900/simulated_rail_dropout_replay.json) preserves exact image hashes, decisions and `simulated_board_rail_dropout=true`. It verifies fallback wiring and some safety gates, while providing no evidence of frequency or live benefit. Do not promote it on this result.
